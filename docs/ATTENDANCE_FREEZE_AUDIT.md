## 高嚴重度

### FZ1 凍結檢查的覆蓋缺口：最常用的單筆核准反而是漏的

**已逐檔 grep 核實**，現行覆蓋矩陣：

| 路徑 | 凍結檢查 |
|------|----------|
| 申請建立（leave／overtime／missed-clock／shift-exchange 主 route） | ✅ |
| 通用批次核准（`api/batch-approve`） | ✅ |
| 撤銷/作廢（六條 cancel/void） | ✅（近期修復） |
| **請假單筆核准**（`leave-requests/[id]/route.ts`） | ❌ **零檢查** |
| **加班單筆核准**（`overtime-requests/[id]/route.ts`） | ❌ 零檢查 |
| **請假專用批次**（`leave-requests/batch/route.ts`——BatchApproveBar 的 endpoint） | ❌ 零檢查 |
| **排班寫入**（`api/schedules`，含批次/模板/複製） | ❌ 零檢查 |
| **天災假設立/編輯/刪除**（`api/disaster-day-off`） | ❌ 零檢查 |

**後果**：
1. 凍結月份的待審請假：從審核儀表板批次核准 → 被擋；同一筆點進去**單筆核准 → 放行**（核准會扣特休、改班表 FDL——凍結月資料被改）。審核人一旦發現這個「繞過法」，凍結對核准動作形同虛設。
2. 排班管理可以直接改**已凍結月份的班表**——而班表是工時、扣薪、全勤的計算基準（第八份 B8：records 顯示重算優先，改凍結月班表會讓已結算薪資與顯示工時分歧）。
3. 天災假可設立在已凍結月份（改寫班表為 TD），刪除天災假也會回寫凍結月班表。

**修正方向**：抽共用 guard（輸入日期陣列 → 檢查 → 統一 409 回應），五個缺口路徑各補一行；`api/schedules` 與 `disaster-day-off` 對**目標日期**檢查。與第九份 P1 的修復模式一致，照抄即可。

### FZ2 凍結內建第二套簡化薪資引擎

**位置**：`api/attendance-freeze/route.ts:140-235`（POST 的 autoCalculatePayroll）、`:243-354`（`calculateAndCreatePayroll`）

凍結時勾「自動計算薪資」，會為所有尚無該月薪資的在職員工，用**這個路由檔內自帶的簡化演算法**產生正式 `PayrollRecord`。與正式流程（`payroll/generate` → `payroll-processing`）的差異：

| 項目 | 正式流程 | 凍結自動版 |
|------|----------|-----------|
| 加班費費率 | 4/3、5/3 分段（salary-utils） | **`totalOvertimeHours × hourlyRate`，1 倍**（L277）——**少付 33–67%** |
| 核准加班過濾 | `resolveApprovedAttendanceOvertime`（只算核准時數） | **直接加總 AttendanceRecord.overtimeHours**——含未核准時數（B9），**多算** |
| 補償模式 | 補休型加班不發錢 | **不看 compensationType——補休型也發加班費**（雙重補償） |
| 考勤扣薪 | 有（遲到/早退/缺勤） | **無** |
| 特休/補休有薪時數 | 有 | **無** |
| 月份範圍 | 台灣月界 | **UTC 月界**（L249-250 `new Date(payYear, payMonth-1, 1)`）——台灣每月 1 號的考勤**漏算** |

**卡位效應**（最傷）：正式流程對已存在的 `PayrollRecord` 跳過——凍結時自動產生的**錯誤薪資會卡住正式流程**，之後薪資管理頁跑 generate 顯示「已存在，跳過」，錯誤數字直接進發放。

**修正方向**：刪除 `calculateAndCreatePayroll`，autoCalculatePayroll 改為呼叫正式的 payroll 產生邏輯（同一函式）；或砍掉「凍結順便算薪資」功能、只保留提示訊息引導到薪資管理頁（L218-223 的訊息分支已經寫好了）。**兩套薪資引擎並存是本系列（OT2 費率雙引擎、AR2 四套遲到）同構問題中金額最大的一個。**

### FZ3 未生效的手動凍結會遮蔽週期凍結

**位置**：`src/lib/attendance-freeze.ts:51-99`

檢查邏輯：先找該月的手動凍結記錄——**找到就不再查週期設定**（L69 只在 `!freeze` 時 fallback）；找到但 `now < freezeDate`（尚未生效）→ 直接回傳「未凍結」（L99）。

**攻擊/誤用路徑**：週期設定已把 6 月凍結（每月 5 日自動生效）→ 管理員為 6 月建一筆 `freezeDate` 在未來的手動凍結記錄 → 檢查邏輯只看手動記錄 → 未到生效日 → **6 月解凍了**。「新增一筆凍結」的操作實質效果是解凍——語意完全顛倒，且無任何警示。若這其實是刻意的「例外延後凍結」機制，它沒有文件、沒有稽核（FZ6）、且 UI 上看起來就是「新增凍結」。

**修正方向**：手動記錄未生效時仍應 fallback 檢查週期設定（取兩者的「較嚴」結果）；若「例外延後」是需求，做成明確的獨立操作（含稽核與確認提示）。

## 中嚴重度

### FZ4 解凍功能（已修正）

**修正**：`api/attendance-freeze/route.ts` 已新增管理員限定的 `PATCH`；前端 `attendance-freeze/page.tsx` 提供停用/重新啟用入口，強制輸入原因並寫入稽核紀錄。

凍錯月份（選錯年月、提早凍結）現在可由管理員以有原因的停用操作修正；重新啟用時會檢查同月是否已有其他生效中的凍結設定。

**保留風險**：停用後可修改凍結月份資料，仍應依稽核紀錄與管理員作業規範控管；本次不新增第二層密碼或雙人覆核流程。

### FZ5 凍結與自動薪資非交易、失敗不落地

**位置**：`route.ts:205-228`

凍結記錄先建立（L159），薪資逐員工計算，單人失敗只 `console.error` + 計數——回應訊息只有「失敗: N 筆」，**哪些員工失敗無從查起**（console 滾走就沒了）；且凍結已生效，無回滾。失敗員工的薪資之後由正式流程補（`skipped` 邏輯允許），但沒人會知道要補誰。

**修正方向**：FZ2 修復（改呼叫正式流程）後此問題大半消失；保留的部分：失敗清單回傳到前端顯示 + 寫入通知。

### FZ6 凍結建立無稽核

`AuditAction.ATTENDANCE_FREEZE` 在 `src/lib/audit.ts` **已定義**（第八份稽核時確認過枚舉存在），但凍結路由零 `logAudit` 呼叫——高危操作（直接決定一個月的資料可否修改、還會產生薪資）無操作紀錄。P0 設定稽核的接線清單應把此路由列入首批。

### FZ7 `parseFreezeTime` 無驗證——週期凍結可靜默失效

**位置**：`attendance-freeze-rules.ts:22-25`

`freezeTime.split(':')` 無格式驗證——設定存入 `"25:99"` 或空字串 → NaN → `Date.UTC(..., NaN-8, NaN)` → Invalid Date → `now >= InvalidDate` 恆 false → **週期凍結整個靜默失效**，所有「過往月份自動凍結」的保護消失，無任何錯誤或告警。設定寫入端有沒有驗證是另一層（依本系列經驗不能指望），lib 層應自帶 fallback（解析失敗用預設 18:00 + logger.error）。

## 低嚴重度

### FZ8 `checkMultipleDatesFreeze` N+1（已修正）

已改為先按台灣年月去重，再呼叫 `checkAttendanceFreeze`；30 天單月申請現在只檢查一次，跨月長假則每個月份檢查一次。

### FZ9 凍結前提醒永遠不會發（引用第五份）

`ApprovalFreezeReminder` 現已由 `process-overdue` cron 消費：以台灣日曆日期計算距離下一次週期凍結的天數，達到設定的兩組提醒日且超過提醒時間後，呼叫既有 `notifyBeforeFreeze` 發送給管理員；通知資料會帶有提醒鍵，避免 cron 重跑造成同一提醒日重複發送。

### FZ10 未來 freezeDate 的佔位中間態

POST 允許 freezeDate 為未來，現在明確將其定義為預約凍結：API 與前端會顯示「已排程、尚未生效」，且仍以同月防重避免多筆互相矛盾的凍結設定。

## 建議修復順序

1. **FZ1 覆蓋補齊**（共用 guard + 五路徑接線）——1 天。凍結的意義取決於覆蓋面，這是根本。
2. **FZ2 移除第二套薪資引擎**（改呼叫正式流程或只留提示）——半天到 1 天。錢的問題優先。**修復前先盤存量**：`SELECT * FROM payroll_records` 比對凍結自動產生的記錄（`hourlyWage = employee.hourlyRate` 且無扣薪明細者）是否已發放。
3. **FZ3 遮蔽邏輯修正 + FZ4 解凍端點（含稽核）+ FZ6 凍結稽核**——一批做，1 天。
4. **FZ7 時間解析防呆**——半小時。
5. **FZ5/FZ8/FZ9/FZ10** 見縫插針（FZ9 併第五份方案）。

## 與系列文件的關聯

- FZ1 是第九份「撤銷路徑缺防護」修復後**殘留的另一半**：當時盤的是撤銷，這次盤出單筆核准與排班/天災假——建議這次直接做成「凍結覆蓋 checklist」（任何會寫入考勤/班表/申請狀態的路由都過一遍），一次收斂。

- FZ9 接第五份通知整併、FZ6 接 P0 設定稽核——既有計畫的接線清單各補一項即可。
