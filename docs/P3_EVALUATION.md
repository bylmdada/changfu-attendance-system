## 1. 日誌檔案旋轉（核實後翻案：這是快贏，不是 P3）

**現況**：路線圖原判「日誌無分層/旋轉/集中收集」——核實後大部分不成立。`src/lib/logger.ts`（286 行）已有完整等級（DEBUG–CRITICAL）與八類分類，且**已整合 Sentry**（`@sentry/nextjs`）——集中式錯誤收集已存在。真正剩的缺口只有 PM2 的本機 stdout 日誌檔無限增長。

**方案**：VPS 上一條命令裝 `pm2-logrotate` 模組（保留 30 天、單檔 10MB 上限），寫進部署文件。不裝 winston、不建日誌管線。

**完成狀態**：2026-07-02 已於 DigitalOcean VPS 安裝並啟用 `pm2-logrotate`。目前設定：單檔 `10M` 輪轉、保留 `30` 份、壓縮啟用、檔名時間格式 `YYYY-MM-DD_HH-mm-ss`、PM2 module log 也納入輪轉。部署文件已補上設定指令。

## 2. 全勤遲到/早退自動判定

**現況**：`src/lib/perfect-attendance.ts` 的扣發規則已定義「遲到/早退每次扣 0.5 天」（L245–246 註解），但 L233 有 `TODO: 未來可新增遲到/早退判斷邏輯`——**扣法有了，判定沒有**：系統目前不會從打卡時間 vs 班表自動判定遲到早退，全勤計算等於漏算這兩類。

**完成狀態**：2026-07-02 已補上 `src/lib/perfect-attendance.ts` 的班表比對。全勤獎金計算現在會讀同月 `Schedule`，以台灣時區比對 `AttendanceRecord.clockInTime/clockOutTime` 與班表 `startTime/endTime`：晚於開始時間計遲到，早於結束時間計早退；每次依既有規則扣 0.5 天。已補 `src/lib/__tests__/perfect-attendance.test.ts` 覆蓋遲到、早退與獎金扣發。

**待決策**：目前是無寬限版。若 HR 確認遲到/早退有寬限分鐘數，再把寬限值接入系統設定。

## 3. LINE 通知渠道

**現況**：核實確認**無任何 LINE/SMS 整合**（`realtime-notifications.ts` 枚舉裡的 `SMS` 只是字串，無發送實作）。現有渠道：站內（已落地 DB + 鈴鐺）、Email、Web Push。

**方案**：LINE Messaging API（官方帳號）——員工掃 QR 綁定（存 LINE userId 於 Employee），`sendNotification()` 加 LINE channel，緊急類事件（災防假公告、凍結提醒）優先走 LINE。3–5 天含綁定流程。

**觸發條件**：站內/Email 通知的觸達率不足（鈴鐺上線後可觀察）；或出現「非上班時間需要立即通知全員」的場景（颱風假是典型）。

**建議**：等鈴鐺跑一季看數據。若要做，**LINE 優先於 SMS**——台灣滲透率高、免費額度夠幾百人規模、可傳富文本。

## 4. 離線打卡

**現況**：核實發現 **PWA 基礎已存在**——`public/manifest.json`、`public/sw.js`、`public/offline.html`、`public/icons/`、`ServiceWorkerRegistration.tsx` 都在（為推播而建）。離線打卡的技術地基比預想好。

**但真正的難點不是技術**：離線打卡的時間戳由客戶端產生，**伺服器無法驗證**——這是考勤系統的信任邊界問題。員工可調裝置時鐘後「補」離線打卡，GPS 驗證離線時也不可信。

**方案（若做）**：SW 攔截打卡請求入 IndexedDB 佇列，恢復連線後同步；伺服器端對離線提交的紀錄**強制標記「離線補登」**並進主管審核流（等同補打卡申請的簡化版）。5–8 天。

**觸發條件**：P0 已改善 GPS 錯誤提示 + WiFi 驗證後，仍有常態性弱網打卡失敗（特定場域如地下室/工地）——用打卡失敗率數據說話。

**建議**：2026-07-02 決策不做。若未來失敗集中在特定地點，先評估「該地點加 WiFi 驗證白名單」這種零開發解法。

## 5. 快速打卡整合（自 P2 移入評估）

**現況**：核實後，`login/page.tsx` 已有快速打卡完整流程：帳密打卡、GPS 驗證、WebAuthn 生物辨識、今日打卡狀態、提早/延後原因提示，後端 `/api/attendance/verify-clock` 也已有測試。因目前打卡限定手機使用，儀表板入口效益不高，已移除儀表板「今日打卡狀態」與「系統功能」的快速打卡入口。

**結論**：保留登入頁快速打卡分頁與 `/login?mode=quickclock` 直達模式，不在登入後儀表板另外放入口。

**觸發條件 / 建議**：問使用者是否需要「不登入系統只打卡」的場景（如共用平板打卡機）。有就做完，沒有就刪碼——**半成品放著是最差選項**。

## 6. 下拉刷新

**方案**：行動版頁面加 pull-to-refresh 手勢（30 行內的 touch 事件處理，或輕量套件）。1 天。

**建議**：等行動端使用者實際反映「資料不新」再做——多數頁面已有輪詢或操作後刷新，需求可能不存在。

## 7. ARIA 無障礙全面改善

**現況**：modal/toast/icon 按鈕普遍缺 ARIA 屬性，未做鍵盤導航測試。

**方案（若做）**：全站審查 + 補標（`role="dialog"`、`aria-label`、focus trap、Esc 關閉），以共用元件（modal、toast）為先——改一處全站受益。5–8 天。

**建議**：分兩層——**新寫的共用元件從現在起就守規範**（成本近零，寫進團隊慣例即可）；存量改造等出現實際需求（視障/輔具使用者入職、或政府機關合規要求）。

## 8. i18n 多語系

**現況**：全站繁中硬編碼，字串散落數百個檔案。

**方案（若做）**：next-intl 或 next-i18next，抽出全部字串 + 翻譯。以本系統規模（50+ 頁）估 10–15 天，且之後每個新功能都有翻譯維護成本。

**建議**：**不做**。這是內部考勤系統，員工全為中文使用者；i18n 是投報比最差的一項。唯一觸發條件：實際聘用非中文員工。

## 9. OpenAPI/Swagger 文件

**現況**：`docs/API_DOCUMENTATION.md` 僅 320 行，對 70+ 組路由覆蓋率低。

**方案（若做）**：路由層引入 zod schema（現多為手寫驗證）→ zod-to-openapi 生成 → Swagger UI。因需先補 schema，實際是 5–10 天的改造。

**建議**：**不做**。API 文件的價值在「外部消費者」——本系統前後端同倉、單團隊，型別已由 TypeScript 保證。觸發條件：出現外部串接方（如集團 HR 系統要拉考勤資料）。屆時也只需為**對外的那幾支** API 寫規格，不必全站。

## 10. SMS 通知渠道

**建議**：**不做**。LINE（#3）在台灣情境完全覆蓋 SMS 的場景且免月費；SMS 每則計費、還要接電信閘道。除非未來有「無智慧型手機員工」的硬需求。
