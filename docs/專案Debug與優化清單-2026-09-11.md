## 3. 薪資、假期與帳務必修

### D01｜月加班費錯用單日計算器

- **位置**：`src/lib/payroll-calculator.ts:165–190,208–238`；`src/lib/overtime-calculator.ts:65,125`；`src/lib/payroll-processing.ts:866`。
- **流程**：薪資試算、產生、保存 API → `computePayrollForEmployee` → `calculateMonthlyPayroll`。
- **根因**：先將整月同類加班時數加總，再只呼叫一次具有單日級距與上限的計算器，遺失日期分界。
- **重現**：時薪 150 元，每個工作日均有 2 小時應付平日加班；下列預期值依專案現有單日公式相加。

| 工作日數 | 目前月加班費 | 逐日合計應得 |
|---:|---:|---:|
| 2 | 900 | 800 |
| 3 | 900 | 1,200 |
| 10 | 900 | 4,000 |

- **最小修正**：按員工工作日及加班類型合併同日資料後，逐日計費再加總；月時數分類繼續供報表使用。保留僅補休、自選補償的既有規則。
- **驗收**：以上三例、兩個休息日、兩個國定假日、同日多筆、僅補休、自選補償，均斷言精確金額。
- **資料處理**：修正後先輸出歷史薪資差異清單，確認受影響月份與補償模式，再處理已發放薪資；不可直接批次覆寫。

### D02｜特休扣帳忽略小時與台灣日期

- **位置**：`src/lib/annual-leave.ts:6–26`；`src/app/api/leave-requests/[id]/route.ts:176–186`。
- **根因**：`getAnnualLeaveYearBreakdown` 去除起訖時間，按 UTC 日期逐天加 1。申請計算則以有效工時除以 8 換算天數，見 `src/lib/leave-management-helpers.ts:242–263`。
- **重現**：同日 09:00–13:00 的 4 小時有效特休被扣 1 天；台灣 2027-01-01 00:00–08:00 被分成 2026 年與 2027 年各 1 天。
- **影響**：單筆、批次核准及取消／作廢共用此 helper，特休餘額與年度歸屬可能錯誤。
- **最小修正**：重用 `getAnnualLeaveHoursByDate`／`calculateLeaveHoursByDate`，按台灣工作日年度彙整有效工時，再除以 8；核准與沖回使用一致的扣帳分攤依據。
- **驗收**：2 小時、4 小時、5 分鐘、休息時段、跨午夜、跨年；扣帳天數等於有效工時／8，取消與作廢精確復原。
- **資料處理**：舊紀錄需先對帳，避免用新公式直接沖回舊公式曾扣除的數量。

### D03｜單筆與批次核准產生不同帳務結果

- **入口**：`src/app/leave-management/page.tsx:1955` 使用 `/api/leave-requests/batch`；`src/app/approval-dashboard/page.tsx:603` 使用 `/api/batch-approve`。
- **對照**：單筆 `src/app/api/leave-requests/[id]/route.ts:151–190` 已同步特休班表工時及補休帳。
- **缺漏**：`src/app/api/leave-requests/batch/route.ts:117–149`、`src/app/api/leave-requests/batch-approve/route.ts:90–109` 漏同步 `specialLeaveHours`；`src/app/api/batch-approve/route.ts:278–307` 另漏 `applyCompensatoryLeaveUse`。
- **影響**：同一假單由不同畫面核准，可能得到不同特休有薪工時、補休餘額與薪資；批次補休也可能跳過餘額不足檢查。
- **最小修正**：將既有核准資料異動集中於一個共用函式，讓單筆與三個批次入口在同一交易更新狀態、特休帳、班表與補休帳。
- **驗收**：相同假單分別由四個入口核准，比對帳務與薪資結果一致；補休不足、重送核准、交易失敗均不得留下部分異動。

### D04｜部分日有薪假被當成遲到／早退扣薪

- **位置**：`src/lib/payroll-processing.ts:419–472,860–864`；`src/lib/annual-leave-schedule-accounting.ts:27–36`。
- **條件**：考勤扣薪設定 `enabled=true`；目前程式預設為 false，正式設定未查。
- **根因**：有薪假總時數只用於全日排除／缺勤計算；實際有打卡時，仍直接拿原班表起訖計算遲到早退，沒有核准請假區間。
- **重現**：09:00–18:00 班、工時 8 小時，09:00–11:00 已核准特休，11:00 到班、18:00 離班、時薪 150，仍被算遲到 120 分鐘並扣 300 元。
- **最小修正**：扣薪以有效排班區間減去已核准有薪假及休息時段後的缺勤分鐘計算，沿用現有區間交集工具。
- **驗收**：上午、下午、中間時段有薪假、跨夜、真遲到與請假並存；已核准時段不扣，真正缺勤部分仍正確計算。

### D05｜計時人員被重複扣除未出勤工時

- **位置**：`src/lib/payroll-calculator.ts:243–252`；`src/lib/payroll-processing.ts:860–864,887–890`。
- **條件**：員工類型 `HOURLY` 且啟用考勤扣薪。
- **根因**：計時本薪已是實到工時乘時薪，下游又不分員工類型扣除遲到／早退金額。
- **重現**：時薪 150、排班 8 小時、實到 7 小時，本薪已降為 1,050，再扣 150，其他保險稅額前只剩 900。
- **最小修正**：避免再扣已從計時本薪排除的工時；固定月薪的缺勤扣款依既有規則保留。
- **驗收**：相同遲到、早退、全日缺勤案例分別測 MONTHLY／HOURLY；計時工時只影響薪資一次。

## 4. 權限與資料保護必修

### D06｜員工列表繞過銀行資料的角色限制

- **位置**：`src/app/api/employees/route.ts:44–50,117–147`；`src/lib/schedule-management-permissions.ts:25–34`；`src/lib/attendance-permission-scopes.ts:114–145`。
- **根因**：具有部門排班權限的非 ADMIN／HR 可查員工列表；Prisma 查詢使用 `include`，未限制 Employee scalar 欄位，整筆資料直接回傳。
- **明確對照**：專用銀行 API 在 `src/app/api/employees/bank-accounts/route.ts:62–63` 限 ADMIN／HR，`:113` 預設遮罩帳號；一般員工列表卻可取得明文 `bankAccount`。身分證欄位儲存值有加密，本報告不將它描述為明文身分證外洩。
- **最小修正**：非 ADMIN／HR 的回應明確選取排班所需欄位，例如 id、員編、姓名、部門、職位、啟用狀態，保留既有部門範圍限制；核對各 caller 的必要欄位。
- **驗收**：只有排班權限的帳號能取得授權名單，但 JSON 不含完整銀行帳號、身分證儲存值、薪資、地址等非必要欄位；銀行管理 API 仍回 403。

### D07｜眷屬證明附件缺少實際下載授權

- **位置**：`src/app/api/my-dependents/attachments/route.ts:107–126`；`src/app/health-insurance-dependents/page.tsx:871`。
- **根因**：身分證、戶籍等證明檔寫入 `public/uploads/dependent-attachments`，前端直接開啟 `filePath`。取得 URL 後，靜態下載不經申請人／ADMIN／HR 的 API 權限判斷。
- **證據界線**：上傳與列表已有登入、所有權、CSRF 與大小檢查；缺口是檔案實際存放及下載路徑。正式 Nginx 是否另有阻擋尚未驗證。
- **最小修正**：沿用既有受保護附件模式，改存 public 外，透過附件 ID 查 DB、確認申請人或 ADMIN／HR 後讀檔；同步遷移歷史檔案、更新路徑並停用舊公開網址。
- **驗收**：未登入、其他員工、已登出皆不能下載；申請人及授權管理員可下載；舊公開 URL 不再回檔案內容。

### D08｜角色降權沒有立即生效

- **位置**：`src/lib/auth.ts:50,82–99`；`src/app/api/employees/[id]/route.ts:458–465,482–485`。
- **根因**：共用驗證只查帳號是否啟用與 session 是否相符，回傳 JWT 原角色；角色更新未撤銷 session。Token 有效期為 8 小時。
- **隔離重現**：DB 角色已為 EMPLOYEE、session 相符，舊 JWT 角色為 ADMIN；`getUserFromToken` 仍回 ADMIN。
- **最小修正**：利用每次已存在的 DB 查詢取得最新角色，回傳時以 DB 為準；檢查其他具權限意義的身分欄位是否也需要同步。
- **驗收**：降權後舊 token 呼叫管理 API 立即 403／401；停用、正常 session 及新登入行為不退化。

### D09｜登出只清 Cookie，舊 token 仍有效

- **位置**：`src/app/api/auth/logout/route.ts:22–28`；`src/lib/auth.ts:95–99`。
- **隔離重現**：登出回 200，但沒有 DB session 異動；原 token 再驗證仍成功。
- **最小修正**：驗證登出的原 session，以 userId 與 currentSessionId 條件更新為 null，再清 Cookie。條件更新避免舊裝置的延遲登出誤撤銷新裝置登入。
- **驗收**：登出後重用原 token 回 401；舊 session 登出不影響新的 session；缺失／無效 Cookie 仍可清理瀏覽器 Cookie。
- **測試缺口**：既有 logout 測試主要確認 Cookie 及 CSRF，需增加伺服器 session 撤銷斷言。

## 5. 部署、備份與版本更新必修

### D10｜Prisma 與服務可能使用不同環境檔／資料庫

- **位置**：`deploy-vps.sh:163–191`；`setup-production.sh:114–140`；`prisma/schema.prisma:7`。
- **根因**：腳本同步 `.env.production`，但只將檔名傳給 setup 子程序；setup 只檢查存在，後續 Prisma CLI 未明確載入該檔。已核對本機 Prisma CLI 自動尋找 `.env` 的實作，與 Next 載入 `.env.production` 的方式不同。
- **條件**：只配置 `.env.production` 且 SSH 未 export DATABASE_URL，或兩份 env 指向不同 DB。
- **影響**：migration 缺環境變數，或遷移成功但更新的是另一份資料庫。
- **最小修正**：CLI 明確讀取指定環境檔，統一 runtime、migration、backup 解出的 SQLite 絕對路徑；在停止服務前核對。修正範本中可能造成 `prisma/prisma` 的相對路徑歧義。
- **驗收**：隔離目錄只有 `.env.production` 仍可讀取設定；衝突路徑在停機前被拒絕；三個用途實際指向同一個檔案。

### D11｜部署失敗缺少可靠回復流程

- **位置**：`deploy-vps.sh:136–161,185–198,209–218`。
- **根因**：先原地 rsync 程式與 `.next`，再於 live 目錄安裝依賴，之後才停止 PM2；migration 失敗直接退出，後段重啟不會執行。腳本本身未建立當次部署前資料及舊產物備份。
- **影響**：部署中可能讀到新舊混合檔案；migration 失敗後服務可能持續停止。
- **最小修正**：先在暫存位置完成可離線準備的工作；live 異動前取得且驗證當次 DB／舊產物快照；停機切換後執行 migration 與健康檢查，失敗依 schema 相容性及快照恢復。
- **驗收**：隔離模擬安裝失敗、migration 失敗、健康檢查失敗，確認可回到可用版本且資料完整；備份失敗不得繼續。不能只加無條件 `pm2 restart`，它可能啟動不相容的新程式。

### D12｜migration 無法從空資料庫重建

- **位置**：`setup-production.sh:139–140`；`deploy-vps.sh:191`；`prisma/migrations/20260113_clock_reason_fields/migration.sql:2`。
- **根因**：setup 可建立空 DB，但排序第一個 migration 直接 `ALTER TABLE attendance_records`；migration 目錄沒有建立 employees、attendance_records 等核心表的初始基線。
- **影響**：新機或災難重建照目前主線，會因缺表卡住；不代表既有正式 DB 現在缺表。
- **最小修正**：補可重播的初始 baseline，以及既有資料庫如何對齊 migration 歷史的步驟；保留已發布 migration，不以一般 `db push` 掩蓋歷史。
- **驗收**：空 DB 可依序套完全部 migration，結構符合 schema；既有 DB 複本完成對齊後可重跑，資料不流失。

### D13｜備份鎖的清理不區分擁有者

- **位置**：`scripts/backup-database.sh:29–33,96–108`；正式 cron 安裝見 `setup-production.sh:155–163`。
- **根因**：取得鎖前先註冊 EXIT cleanup；第二個程序因鎖已存在而退出時，cleanup 仍移除第一個程序的鎖目錄。
- **影響**：第三個程序可闖入並行備份；同秒執行還可能碰到同名備份／驗證檔。
- **最小修正**：成功取得鎖後才註冊清理，或只允許成功取得鎖的程序釋放它。
- **驗收**：A 持鎖時 B、C 均失敗退出，鎖仍保留；只有 A 結束才釋放。使用隔離測試目錄與假 DB，不碰正式備份。

### D14｜Service Worker 讓使用者持續看到舊版本

- **位置**：`public/sw.js:1,65–95`；`src/components/ServiceWorkerRegistration.tsx:14`；`src/app/layout.tsx:34`。
- **根因**：所有非 API GET 都採 Cache First，包含 HTML 導航；快取命中後不再查網路，快取名稱固定。服務重新部署不必然更新已快取頁面。
- **隔離重現**：第一次導覽取得 release-A；模擬伺服器改為 release-B 後再次導覽仍回 A，兩次導覽合計只 fetch 一次。
- **最小修正**：快取限於必要靜態資源；HTML 導航採網路優先或交給網路。發布修正版時清理既有錯誤快取，保留現成離線提示頁即可。
- **驗收**：同一已開啟過網站的瀏覽器在部署後重新導覽會取得新頁面；舊 chunk 不會令頁面壞掉；斷線仍有明確提示。

### D15｜監控資料與「備份完成」並非實際結果

- **位置**：`src/lib/system-maintenance.ts:308–335,387–404,456–477,666–692,775–782`；`src/app/api/system-maintenance/route.ts:56–90`。
- **根因**：API 錯誤率與安全評分使用 Math.random，安全弱點固定為 0；備份動作只等待 5 秒，卻由共用執行器標成 completed。
- **影響**：管理員可能把未量測的數字與沒有產物的作業當成真實健康／備份證據。專案另有真實 SQLite 備份腳本，不能因此誤寫「完全沒有備份」。
- **最小修正**：移除模擬評分；未量測項目顯示「尚未檢查」。停用假維護動作，或讀取既有正式備份腳本的結果與產物資訊，不需另建一套排程平台。
- **驗收**：無有效備份產物不得顯示成功；未執行安全檢查不得顯示 0 弱點；測試資料來源中斷時畫面正確標記未知／失敗。
